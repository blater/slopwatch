# Agent-assisted Fix implementation plan

Status: implementation in progress on `feature/agent-assisted-fix`.

## Product outcome

Pressing `x` on a file opens a compact Fix form. Pressing `r` starts a job that
refactors the selected file until its Slopwatch SCORE reaches the chosen target.
The same domain API already accepts multiple targets so Files-view multi-select
can be added without changing the job or adapter contracts.

A fix job:

1. reads the selected targets and their measurements through Slopwatch services;
2. creates a detached worktree for that job;
3. asks the selected agent to refactor only the allowed paths;
4. measures the resulting files with Slopwatch;
5. sends the new measurements back to the agent when the target is not met;
6. repeats without a Slopwatch attempt cap or wall-clock timeout;
7. commits and pushes the configured branch when the target is met;
8. optionally creates the configured pull request; and
9. removes the temporary worktree while retaining compact job history.

There is no pre-commit review state, manual Publish action, manual Retry action,
candidate archive workflow, or action menu. Git branches and pull requests are
the review and retention mechanism. Cancel is the sole user command on a job.

## Architecture

### Cohesive agent boundary

`agent.Strategy` is the provider-neutral execution boundary. The coordinator
depends on the agent package, never on Codex, OpenAI, Claude, Grok, a provider
SDK, a CLI process, or provider authentication details.

The boundary owns:

- provider discovery and readiness;
- capability catalogues for model, effort and delegation;
- typed execution requests;
- streamed normalized events;
- normalized completion, failure, usage and session identity;
- provider cancellation; and
- provider-specific settings schemas.

An adapter receives all job input through its request. It must not read the
analysis cache, preferences file, UI model, coordinator journal or Git delivery
state. The analysis service owns cached measurements and supplies an immutable
baseline through the coordinator API. Authentication remains provider-owned or
is resolved from a configured secret reference at execution time.

Initial adapters are:

- Codex App Server, using the installed `codex` executable and its existing
  ChatGPT or API-key login. This is the default choice.
- OpenAI Responses API, using an API-key reference.

Adding Claude CLI/API, Grok or another provider requires a new strategy and
descriptor registration. It must not require changes to the coordinator, job
state, prompt compiler, analysis service, worktree service or Agents UI flow.

### Coordinator

The coordinator is the only owner of job transitions. Provider events are
observations, not authority to declare a score or delivery result. The
coordinator schedules independent pools for agents and verifiers and accepts
new jobs while others are active.

The normal state sequence is:

```text
QUEUED → PREPARING → RUNNING → VERIFYING
                    ↑             │
                    └─ target not met

VERIFYING → COMMITTING → SYNCING when an external result must be reconciled
          → DONE

any active state → CANCELING → CANCELED
any unrecoverable error → FAILED
```

FAILED, DONE and CANCELED jobs do not reserve their target files. A user may
start another fix immediately. On restart, uncertain Git or pull-request
effects are reconciled automatically from the durable journal; the user is not
asked to peck a Retry or Resume command.

### Worktrees and concurrent delivery

Every job gets a detached worktree based on the recorded source revision.
Agents can therefore edit overlapping repository content without touching the
user's checkout or each other's working directories. Jobs deliver to distinct
configured branches. An existing local or remote branch is reported clearly;
Slopwatch never force-pushes or overwrites it.

The branch template is user-configurable. `{job}`, `{job-short-id}` and target
tokens are generated by Slopwatch; users do not have to invent internal IDs and
organisations are not required to include one. Job, attempt, draft and command
identifiers use the `goname` package rather than GUID-shaped strings.

Successful delivery creates a commit, creates the configured branch, pushes it,
and optionally creates a pull request. Slopwatch then removes the temporary
worktree. Pull requests may be draft or ready for review according to settings.
The base branch is a user choice and is checked when PR delivery is prepared.

### Prompt compilation

The master agent prompt is a global Fix Default stored in preferences. It is
edited from Settings → Fix Defaults → Agent prompt in a full-screen editor. A
fix instance never detaches or edits its own copy.

Supported template values include:

- `{targets}`
- `{target_score}`
- `{focus_metrics}`
- `{change_scope}`
- `{allowed_paths}`
- `{baseline_scores}`
- `{validation_plan}`
- `{branch}`

The compiler combines the rendered master prompt with a short invariant
boundary stating which worktree and paths the agent may edit and that Slopwatch
owns measurement and Git delivery. Agent-generated claims never replace fresh
Slopwatch measurements.

SCORE is always the first focus metric and cannot be switched off. Enabled and
measured component metrics may be selected as additional emphasis. Metrics that
are disabled or unavailable for the target language are not shown.

## User experience

### Fix form

The form is compact and responsive. It shows `READY TO FIX` when preparation
succeeds. Essential fields are:

- target SCORE, remembered globally;
- focus metrics, starting with SCORE;
- agent;
- model;
- effort;
- change scope;
- delivery mode; and
- branch name.

Delegation is hidden when the adapter offers only one choice. Validation is
hidden when it has no usable values. Provider labels are short. `r` runs the
fix; preview and per-job prompt editing are absent.

### Agents view

`Tab` switches between Files and Agents. The Agents table is responsive rather
than designed for a 200-column terminal. It prioritizes readable activity text
and uses otherwise empty width before truncating it. The selected job expands
to show files, each file's relevant SCORE/component measurements, and the file
name at the right edge where space permits. Disabled or unmeasured metrics are
omitted.

The title bar shows only `AGENTS n`, where `n` is the number of agents currently
executing. Historical and canceled jobs are not counted.

Hotkeys are direct actions:

- `i`: Inspect the selected job;
- `l`: open its sanitized log;
- `d`: open its diff; and
- `C`: cancel that job after confirmation.

Inspect is titled `INSPECT`. It does not duplicate the log. It labels usage as
Tokens, shows the short harness/model/effort tuple, and omits internal policy
state or redundant target prose.

### Settings

The Settings list is alphabetical. Agents shows the fixed provider choices and
their availability, aligned as:

```text
Claude CLI   not available
Claude API   available
Codex        [ACTIVE]
Grok         not available
OpenAI API   available
```

There is no add/remove/test account workflow in the first version. Enter opens
a provider-named connection dialog containing only essential connection fields.
The connection is tested automatically and a failure is rendered clearly
without overwriting content.

Low-frequency adapter controls such as executable path, readiness timeout and
cancellation grace remain preferences-file-only. Settings rows do not append
origin/source blurbs or focused-field explanatory hints.

Configurable operational values include agent/verifier concurrency, retained
job count, transcript retention, actor count, candidate preview sizes, delivery
policy and trusted validation limits. There are no compiled attempt or attempt-
duration caps. An active agent remains connected while it is producing output;
provider readiness timeouts apply only to readiness probes.

Preferences are supplied to services through typed configuration interfaces.
No adapter reads the file directly. Atomic preference writes are desirable but
are not a release blocker for the first preferences implementation; preserving
valid syntax and surfacing write failures are required.

## Cancellation and recovery

Cancel targets one job. It signals the provider through its native cancellation
mechanism, joins provider output, releases file reservations immediately, and
removes the job worktree. Cleanup failure is visible but cannot stop another fix
of the same file.

Application shutdown is not treated as user cancellation. Durable worktree and
delivery identity is retained. On the next start, Slopwatch discovers the exact
worktree and reconciles uncertain branch, push and pull-request effects before
continuing or reporting a plain FAILED state.

Provider output has no inactivity timeout. Bounded waits that start only after
explicit cancellation are adapter preferences and exist solely to finish
process teardown.

## Security and authority

- Agents edit only the job worktree and allowed paths.
- Codex uses provider workspace sandboxing; Responses tools expose rooted file
  operations and no shell, Git or arbitrary network tool.
- The agent never receives Git credentials or delivery authority.
- Slopwatch performs fresh diff inventory and scoring.
- Delivery uses exact commits and create-only refs; no force push or auto-merge.
- Provider text and logs are sanitized before display or persistence.
- Repository preferences cannot introduce credentials, executables or broader
  authority than the user's trusted configuration.

Docker is optional. Normal install, startup, Codex fixes, scoring, branch
delivery and PR delivery do not depend on Docker. A configured validation plan
may use the optional container executor; if Docker is absent that validation
capability is unavailable without breaking the rest of Slopwatch.

## Retention

The configured retained-job count is a rolling history size, not a lifetime
admission quota. Before admitting a new job, Slopwatch compacts the oldest DONE,
CANCELED or FAILED records that no longer own a worktree. Active jobs and a job
whose cleanup failed are never silently deleted. Transcript bytes are trimmed
to the configured per-job value and truncation is represented explicitly.

## Verification and acceptance

Release requires:

- unit coverage for prompt substitution, SCORE presence, automatic iteration,
  reservation release, cancellation and automatic delivery;
- adapter contract tests for normalized events, authentication, cancellation,
  event ownership and terminal ordering;
- restart tests for worktree discovery and uncertain external effects;
- concurrency tests proving new jobs can start while others run;
- responsive TUI tests at narrow, medium and wide sizes;
- no Docker requirement in default build, install or startup;
- `go test ./...` and race tests for the coordinator, Codex adapter and TUI state;
- architecture, security and UX review with no unresolved blocker.

## Follow-up compatibility

The first implementation intentionally supports one configured account per
provider. Multi-select and additional adapters are follow-ups. They extend the
typed target slice and strategy registry; they do not introduce compatibility
branches, migrations, legacy parsing or provider conditionals in the core.
