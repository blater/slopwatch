# Small-sample pprof baseline — 2026-09-19

SHALLOW source estimation has a confirmed CPU and allocation hotspot on small
samples. On 200 Ingres Java files, frontend analysis allocates **6.68 GB** and
cold analysis takes **5.48–5.61 seconds** across three captures. Repeated owner
constraint reconstruction, owner/field discovery, and token-body copying are the
first optimization targets. These baseline measurements precede the disk-storage remediation; no scoring policy was changed.

## Measurements

| Source sample | Files | Cold cache miss | Unchanged warm | One-file comment edit | Cold frontend allocations | Cold JSON bytes |
|---|---:|---:|---:|---:|---:|---:|
| River Java | 40 | 0.608 s | 0.027 s | 0.554 s | 184 MB | 1,205,974 |
| River Java | 200 | 1.435 s | 0.065 s | 1.416 s | 913 MB | 5,741,461 |
| Ingres Java, verified capture | 200 | 5.606 s | 0.086 s | 5.624 s | 6,679 MB | 10,210,258 |
| Slopwatch sourceestimate Go | 140 | 1.012 s | 0.032 s | 0.878 s | 1,381 MB | 2,239,188 |

MB/GB here are decimal allocated bytes, **not retained heap or peak RSS**.
Ingres source size was 4,040,148 bytes before the comment edit, about 188K lines.
River 200 was about 625KB/17K lines; Go was about 416KB/14K lines. File count alone
therefore does not describe workload cost. The Go request allowed 200 files but
only 140 non-test sources existed.

The other two Ingres cold captures took 5.500 s and 5.480 s, allocating 6.679 GB
and 6.687 GB. Normal analysis with cache reads disabled took 5.421 s and 5.581 s
in two captures. The verified warm phase made **zero backend calls**. Cold and
warm paths/scores match; merged incremental paths/scores match the fresh report.

The Java backend roundtrip took 1.486 s of the verified 5.606 s cold run. This
includes process startup, Java parsing/analysis, IPC and frontend protocol decode.
Frontend source estimation follows that roundtrip. Sorting and JSON serialization
took 23 ms for the cold report and 23–26 ms across its four phases. Text table
rendering and dashboard drawing were not measured.

## pprof findings

The verified cold CPU profile contains 4.60 seconds of **frontend** CPU samples.
Cumulative percentages overlap and must not be added.

| Call path | Cumulative frontend CPU |
|---|---:|
| `sourceestimate.analyzeWithAttribution` | 69.78% |
| `gradedOwnerConstraints` | 39.35% |
| `gradeConsistentWrites` | 38.26% |
| `callerDeclaredFields` | 36.09% |
| `gradedFindSurfaceOwner` | 35.43% |
| `matching` | 20.87% |

The sampled cold allocation profile attributes **83.46%** of allocated space to
`gradedEagerBody` (57.15%) and `pruneDeadFalseBranches` (26.32%). Another 6.80% is
in `gradedJavaFields`. Heap profiles are sampled and cumulative from process
startup; only the first cold heap profile is used for these percentages. Per-phase
allocation counters in the table use `runtime.MemStats.TotalAlloc` differences
and include CPU-profiler overhead.

The code explains this concentration:

1. [gradeConsistentWrites](../../../go/internal/sourceestimate/graded_evidence_consistency.go#L3)
   calls `gradedOwnerConstraints(u, op.owner, u.ops)` for an assessed operation.
   That function iterates the owner's operations again. Repeating this across
   operations introduces nested method scans; larger classes can cost far more
   than file-count scaling suggests.
2. [callerDeclaredFields](../../../go/internal/sourceestimate/graded_surface.go#L36)
   rediscovers the owner and rebuilds its field map on every call. It is called
   inside constraint expression, bounds and evidence processing.
3. [gradedEagerBody](../../../go/internal/sourceestimate/graded_eager_body.go#L5)
   appends each retained token to an initially empty slice.
   [pruneDeadFalseBranches](../../../go/internal/sourceestimate/transformation_branches.go#L19)
   allocates a full-length-capacity result even when nothing is removed. Multiple
   passes reconstruct these bodies repeatedly.

**Recommended implementation order:** cache immutable declared-field inventories
per unit/owner; compute owner constraints once for each relevant owner/root set;
reuse normalized token bodies where semantics permit; then profile again before
changing concurrency or cache partitioning. Context-sensitive roots, copied
operations, rewritten bodies and witness receivers need separate identities.
Returning existing slices also requires checking callers for mutation. Preserve
all numeric ratings, evidence metadata and semantic regression results.

## Scope and limitations

The user requested small samples first. No 30K run was attempted and these
measurements do not establish enterprise readiness or a release latency budget.

Samples are deterministic lexical prefixes copied from local repositories into
private workspaces; original sources and the user's cache are untouched. Build
configuration/dependencies are not copied. The sample can concentrate on a few
packages and incomplete semantic contexts. In the Java samples this creates a
broad unit: a comment edit refreshed every sampled file. That is a finding about
this fixture, **not proof that every edit in the original repository refreshes
all its files**. Real configured-unit invalidation needs separate measurement.

The Ingres cold report has 187 numeric SHALLOW results and 13 `not_applicable`
files; all 187 numeric results are marked partial. River 200 has 196 numeric and
4 N/A; Go has 138 numeric and 2 N/A. Diagnostic counts are 108, 58 and 140
respectively. These are incomplete-evidence source samples, not clean semantic
acceptance runs. The harness validates SCORE equivalence, not all evidence fields.

Go CPU profiles do not include Java/other subprocess CPU. A Java Flight Recorder
capture and a structural-host pprof capture are still needed to separate the
backend roundtrip. No claim is made about JVM hotspots, idle watch activity,
process-tree peak memory, filesystem-cold performance, or TypeScript/Rust capacity.
Analysis contexts expire after 45 seconds, but synchronous estimator work need
not promptly observe cancellation; `-test.timeout 3m` is the outer guard.

Environment: macOS Darwin 25.6.0, arm64, Go 1.27.1, GOMAXPROCS=10. CPU model,
installed RAM and `/usr/bin/time -l` resource statistics were unavailable because
sandboxed sysctl calls failed. There was no controlled machine-load isolation.
Cold means empty **application analysis cache**, not flushed operating-system caches.
Base analyzer revision: `fcb101668a9bcdc8346500fe34c7b403a7f38035`.
Backend binary hashes and logs are in [small-sample-results.json](small-sample-results.json).

## Reproduce and inspect

The opt-in test defaults to 40 files and caps samples at 500 files, 2 MiB per file
and 32 MiB total. It skips during ordinary tests. Output must be a new directory
outside the source tree with an existing parent. Build the normal analyzers first
(`make build`) if they are absent or stale.

From the repository root:

```sh
mkdir -p build/performance-profile
GOCACHE="$PWD/build/go-cache" GOPROXY=off go test -C go -c -o ../build/performance-profile/native.test ./internal/native
# This Go installation lacked the prebuilt pprof tool; build its bundled source.
GOCACHE="$PWD/build/go-cache" GOPROXY=off go build -o build/performance-profile/pprof cmd/pprof
cd go/internal/native
SLOPWATCH_PROFILE_SOURCE=/Users/blater/src/ingres \
SLOPWATCH_PROFILE_OUTPUT=/Users/blater/src/slopwatch/build/performance-profile/new-ingres-40 \
SLOPWATCH_PROFILE_FILES=40 \
../../../build/performance-profile/native.test -test.run '^TestPerformanceProfile$' -test.v -test.timeout 3m
```

Set `SLOPWATCH_PROFILE_EXT=.go`, `.ts` or `.rs` to select another language.
The retained capture is `build/performance-profile/ingres-200-verified/`; its
matching binary is `build/performance-profile/native-verified.test`. From root:

```sh
build/performance-profile/pprof -top -cum build/performance-profile/native-verified.test build/performance-profile/ingres-200-verified/cold.cpu.pprof
build/performance-profile/pprof -top -alloc_space build/performance-profile/native-verified.test build/performance-profile/ingres-200-verified/cold.heap.pprof
# Optional local interactive pprof browser (requires Graphviz for graph views):
build/performance-profile/pprof -http=127.0.0.1:8080 build/performance-profile/native-verified.test build/performance-profile/ingres-200-verified/cold.cpu.pprof
```

Tracked evidence: [CPU flat](ingres-200-cpu-top.txt),
[CPU cumulative](ingres-200-cpu-cumulative.txt), [allocations](ingres-200-alloc-top.txt).
Raw profiles, copied sources, source hashes, gzip-compressed reports, the verified
captures' caches, and phase metrics
remain under ignored `build/performance-profile/`. `edit.json.gz` is an incremental
report; its metrics identify replacement paths. Later heap profiles require a
baseline subtraction to analyze per-phase allocations.

The profiling harness received an independent review. It was tightened with
canonical-path isolation, byte bounds, source hashes/runtime metadata, exact
sample inventory checks, a zero-backend warm assertion, replacement-path capture,
incremental/fresh score comparison, and structured phase metrics. Remaining
measurement limitations are documented above. CPU/allocation optimizations remain unimplemented; subsequent lossless disk
compression is recorded separately.

Redundant caches from exploratory captures were removed after recording their
measurements. Full reports were losslessly gzip-compressed and verified. This
reduced the profiling directory from 291 MiB to 94 MiB before cache compaction.
